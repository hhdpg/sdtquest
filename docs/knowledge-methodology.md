# 知识库构建方法论：从原始资料到可检索卡片

> 版本：v1.2　｜　日期：2026-11-24　｜　依据：79 张实测卡片
>
> 本文是一份**可复用的操作手册**：任何新的原始资料（Word 手册、钉钉文档、
> 后端规则文档、线上日志）进入系统时，按本文的步骤处理即可产出合格卡片。
> 所有参数与阈值均来自本项目实测，不是理论推导。

---

## 1. 一句话方法

> **按"用户会怎么问"拆，不按"资料怎么组织"拆。
> 一张卡只回答一个问题，正文 200–500 字，留不住的细节做成关联卡。**

原始资料的组织方式是作者视角（章节、模块、功能树），
用户提问是问题视角（怎么做、为什么不行、这什么意思）。
两者结构完全不同，**必须重新组织，不能直接切块入库**。

## 3. 五个阶段总览

```
① 摄取  →  ② 清洗  →  ③ 拆卡  →  ④ 校验  →  ⑤ 关联
   原文转文本    去噪/还原标题   按卡型切分    结构+语义    建立上下游
```

每个阶段都有明确的输入输出和验收标准，见下文。

## 4. 阶段一：摄取

### 4.1 各类资料的摄取方式

| 资料类型 | 工具 | 命令 |
|---|---|---|
| Word 手册（本地） | `import_docx.py` | `uv run scripts/import_docx.py --dir ./manuals` |
| 钉钉在线文档 | dws CLI | 先取 nodeId，再 `dws drive download --node <id>` |
| Markdown 规则文档 | 直接读 | — |
| 后端枚举 / ErrorCode | 脚本扫描 | 见 §6.5 |
| 前端代码 | `src/parser/` | 只当素材，不直接产卡 |
| 线上日志 | SQL 查询 | `question_records` 表 |

### 4.2 钉钉文档的权限陷阱（实测）

**`dws drive list` 和 `dws drive download` 权限不同**：

- 列目录需要「知识库成员」身份，无权限时报 `forbidden.accessDenied`
- **按 nodeId 下载只需文档自身可见权限，通常能成功**

所以拿不到目录列表时不要放弃——用浏览器登录钉钉文档，
逐个点开从地址栏取 `i/nodes/<nodeId>`，再 `dws drive download --node <id>`。

**注意**：dws 的登录态与浏览器登录态**互相独立**，
浏览器登录不会让 CLI 获得权限，但文档 nodeId 是通用的。

### 4.3 大文件的处理

50MB+ 的手册直接 pandoc 转换会超时。正确做法是分离图片与正文：

```bash
pandoc 手册.docx --extract-media=./media -t markdown-pipe_tables \
       --wrap=none -o body.md
```

实测：50MB 文档 → 51MB 图片 + 147KB 正文。
**99.8% 的体积是截图，正文信息量极小。**

### 4.4 验收标准

- [ ] 转换后的文本包含完整的标题层级
- [ ] 表格结构保留（用 `-t markdown-pipe_tables`）
- [ ] 图片已分离或明确标记
- [ ] 目录区、修订记录、版权页可识别（供下一步清洗）

## 5. 阶段二：清洗

### 5.1 必须清掉的噪声

| 噪声 | 来源 | 处理 |
|---|---|---|
| 目录区 | Word 自动生成 | 整段删除，但**先解析出标题层级**（见 5.2） |
| 修订记录 / 版权页 / 封面 | 文档模板 | 按标题黑名单丢弃 |
| 页码、页眉页脚 | 分页符 | 正则过滤 |
| `[](#_Toc12345)` 锚点 | pandoc 转换残留 | 正则清除 |
| 表格对齐空格 | grid 表格 | 压缩连续空格（实测省 48% 体积） |
| emf/wmf 矢量图 | Word 图形 | 直接删除（无显示价值） |

### 5.2 标题层级还原（最关键的一步）

**问题**：pandoc 常把 Word 标题转成同缩进的列表项，
靠缩进推断层级**完全不可靠**。

**正确做法**：从**目录区**解析「anchor ID → 编号层级」，
再按 anchor ID 精确匹配正文标题。

```
目录里：[2.1.1新增组织 [19](#_Toc28194)](#_Toc28194)
                            ↑ 编号段数 = 层级     ↑ 唯一 ID
正文里：1.  []{#_Toc28194 .anchor}**新增组织/批量组织导入**
                ↑ 用这个 ID 精确匹配，同名标题也不会冲突
```

深度优先级的可靠性排序：

1. **anchor ID → 目录层级**（最准，同名标题不冲突）
2. 标题文本 → 目录层级（兜底）
3. 缩进推断（每 4 空格一级）
4. 默认二级

实测某 50MB 手册：294 个标题通过 anchor 匹配得到正确层级，
仅 5 个走缩进兜底。

### 5.3 另一种情况：纯文本编号标题

部分手册（如 HRMI 系列）**不用 Word 标题样式**，而是纯文本「一、」「1.1」。
pandoc 不会转成 `#` 标题，需要按编号规则还原：

```python
PSEUDO_HEADING_PATTERNS = (
    (r"^第[一二三四五六七八九十百]+[章篇]\s*", 1),   # 第一章
    (r"^[一二三四五六七八九十]+\s*[、.．]\s*", 2),   # 一、
    (r"^（[一二三四五六七八九十]+）\s*", 2),        # （一）
    (r"^\d+\.\d+\.\d+\s+", 4),                      # 1.1.1
    (r"^\d+\.\d+\s+", 3),                           # 1.1
)
```

**判定条件**（必须同时满足）：
- 上一行为空（说明是独立段落，不是列表中间）
- 行长 ≤ 50 字
- 不以句号/问号结尾（标题通常不带句末标点）
- 不在表格块内

### 5.4 一个典型坑：正则吃掉首字

```python
# 错误：\S 会吃掉标题首字
re.compile(r"^\d+\.\d+\s+\S")   # "1.1 列表页结构" → 匹配到"列"，sub 后变成"表页结构"

# 正确：不含 \S
re.compile(r"^\d+\.\d+\s+")     # 只匹配编号和空格
```

### 5.5 验收标准

- [ ] 标题层级与原文档 TOC 一致（抽样 10 个核对）
- [ ] 无目录、无页码、无版权页残留
- [ ] 表格可读（不是一堆对齐空格）
- [ ] 单节长度 ≤ 800 字（超出应继续细分）

## 6. 阶段三：拆卡（核心）

### 6.1 先判断：这段内容属于哪种卡型

这是整个方法论里**最需要判断力的一步**。判断依据是"用户会怎么问"：

| 用户问法 | 卡型 | 判据 |
|---|---|---|
| 「我要做 X，怎么操作」 | **task** | 有步骤、有入口、有按钮 |
| 「为什么不行 / 有什么限制」 | **rule** | 有条件、有阈值、有"否则" |
| 「这个报错是什么意思」 | **trouble** | 有报错原文、有原因、有解法 |
| 「X 是什么意思 / 几种区别」 | **glossary** | 有定义、有枚举、有区分 |
| 「整个流程是怎样的」 | **flow** | 有多个角色、多个环节、有先后 |
| 「这个状态能干什么」 | **state** | 有状态机、有可用操作 |

**判定陷阱**：一段资料里常混着多种卡型。
例如"下单规则"文档里既有「怎么配」（task）又有「每个组织只能用一条」（rule）。
**必须拆开，不能塞进一张卡。**

### 6.2 七类卡型的内容骨架

```
task（任务卡）
  一句话答案（做什么+在哪）
  + 入口（菜单路径）
  + 步骤（1/2/3）
  + 限制（来自后端规则！！）
  + 常见报错

rule（规则卡）
  规则本体（条件 + 结果）
  + 会触发的情况
  + 处理办法
  + 例外

trouble（故障卡）
  报错原文（← 这一条极其重要，见 6.4）
  + 原因
  + 处理步骤
  + 同类报错

glossary（术语卡）
  定义（业务语言）
  + 系统里叫什么
  + 在哪看
  + 相关概念区分

flow（流程卡）
  触发条件
  + 步骤（含角色）
  + 时效/限制
  + 各步细节指向哪张卡 ← 不要重复下游卡内容！

state（状态卡）
  状态含义
  + 这状态能做什么/不能做什么
  + 下一步是什么

faq（问答卡）
  问 → 标准答案
```

### 6.3 切分粒度规则

| 规则 | 数值 | 原因 |
|---|---|---|
| 单卡正文 | 200–500 字 | 语义浓度高，召回准 |
| 超过 500 字 | **必须拆卡** | 语义稀释，见 §2 实测 |
| 一张卡只答一个问题 | 强制 | 多主题卡会答非所问 |
| 步骤条数 | ≤ 9 条 | 超过说明该拆成多个卡 |

**拆卡判断**：如果一张卡里出现了两个"入口"或两个"一句话答案"，就该拆。

### 6.4 三个高价值的抽取技巧

**技巧一：报错原文必须进 trouble 卡的 anchors**

用户是拿报错原文来搜的（"提示缺少成本类型"），
所以报错原文要**一字不改**放进 `anchors`：

```yaml
title: 下单时提示「缺少成本类型」怎么办？
anchors: [缺少成本类型, 成本类型未配置, 非可用成本类型, ...]
```

**技巧二：后端规则必须补上"在哪看"**

后端规则文档写的是「状态大于 IMPORT 则拒绝创建」，
业务人员看不懂 `IMPORT`。改写时要同时做两件事：
1. 术语翻译（`IMPORT` → 「导入」状态）
2. **补操作路径**（去哪个页面看订单状态）

**技巧三：区分"稳定知识"与"易变数据"**

| 类型 | 例子 | 处理 |
|---|---|---|
| 稳定知识 | "成本类型在哪配" | ✅ 入卡 |
| 易变数据 | "我们组织配了哪些成本类型" | ❌ 不入卡，卡里加边界话术 |

易变数据类卡片末尾**必须**加：

```
【说明】具体可选值随组织配置不同而不同，
以下单页实际显示为准，我不能替你查。
```

实测（9B 模型）：**没有这句会编造，有这句 3/3 守住**。

### 6.5 自动化可行度分级

不是所有卡都能自动生成，按可行度分三档：

| 档位 | 来源 | 自动化程度 | 说明 |
|---|---|---|---|
| **高** | 枚举类（`*Enum.java`） | 骨架全自动 | code+desc 直接映射，但"能做什么/下一步"需人工补 |
| **高** | ErrorCode / 校验文案 | 骨架全自动 | 报错原文→title 和 anchors，原因解法人工补 |
| **中** | 规则文档（`business-rules.md`） | 半自动 | 按 bullet 切分自动，**改写成人话需人工** |
| **中** | FAQ 文档 | 半自动 | Q/A 结构清晰，可直接切，但要补 anchors |
| **低** | 操作步骤类手册 | 需人工 | 大量"如下图点击"，脱离截图无意义 |
| **低** | 前端代码 | 仅作素材 | 只提取入口、字段名、按钮名 |

**结论**：FAQ 和规则文档是**投入产出比最高**的来源，
操作步骤手册的性价比最低（详见 §2.3 的漏斗数据）。

### 6.6 验收标准

- [ ] 一张卡只回答一个问题
- [ ] 正文 200–500 字
- [ ] `one_liner` 单行 ≤ 80 字，先给答案
- [ ] `title` 是用户问法，不含代码名
- [ ] `anchors` ≥ 3 个，覆盖用户的说法
- [ ] `source_ref` 能定位到具体章节
- [ ] 配置类卡片带边界话术

## 7. 阶段四：校验

### 7.1 结构校验（机器自动）

`scripts/validate_cards.py` 检查以下项，任一不通过则整卡拒绝入库：

| 检查项 | 规则 | 违反后果 |
|---|---|---|
| 必填字段 | 10 个必填 | 卡片不完整 |
| 卡型合法 | 七类之一 | 无法归类展示 |
| `one_liner` 长度 | ≤ 80 字 | 首句答案失效 |
| `body` 长度 | 60–600 字 | 语义稀释或信息不足 |
| `anchors` 数量 | ≥ 3 个 | 召回不足 |
| **代码名泄漏** | 标题/一句话答案不含表名、驼峰名、枚举常量 | 业务人员看不懂 |
| `card_id` 格式 | `module-cardtype-slug` | 难以维护 |
| card_id 重复 | 全局唯一 | 互相覆盖 |
| **关联断链** | `related` 指向的卡必须存在 | 串联失败 |
| **孤立卡** | 至少有一个关联（出或入） | 检索时无上下文 |

### 7.2 代码名泄漏检测（双视图保障）

业务人员看到 `us_order`、`handleCreateOrder`、`IMPORT` 会困惑。
校验器用正则拦截这几类：

```python
CODE_LEAK_PATTERNS = (
    (r"\bus_[a-z_]+\b", "表名"),           # us_order
    (r"\b[a-z]+[A-Z]\w*\b", "驼峰标识符"),   # handleCreateOrder
    (r"\b[A-Z][A-Z0-9_]{3,}\b", "枚举常量"), # IMPORT
    (r"/api/[a-zA-Z0-9/_-]+", "接口路径"),
)
```

**只检查 `title` 和 `one_liner`**——因为这两个字段会直接展示给用户。
`body` 里允许出现代码名（用于追溯），但生成答案时会剔除。

### 7.3 语义校验（人工抽检）

结构合规不代表内容有用。以下三项必须人工抽检：

| 检查项 | 抽检比例 | 判据 |
|---|---|---|
| 路径准确性 | 100% | 菜单路径、按钮名与系统实际一致 |
| 术语改写分寸 | 30% | 技术词是否翻译正确（`IMPORT`→「导入」是否准确） |
| 答案完整性 | 30% | 是否漏了关键限制条件 |

**为什么必须人工**：这些是"事实正确性"问题，
自动化只能查格式，查不出"菜单路径写错了"。

### 7.4 召回校验（机器自动）

`scripts/eval_cards.py` 用两套问题测试：

```python
# 1. 本域问题：应该命中正确卡片
CASES = [("怎么下单", "order-task-create"), ...]

# 2. 跨域问题：应该诚实返回"没资料"
KNOWN_GAPS = ["库存怎么管理", ...]
```

判定标准：

| 指标 | 合格线 | 当前实测 |
|---|---|---|
| 本域命中率 | ≥ 95% | 100%（23/23） |
| 预期卡片正确 | ≥ 90% | 100% |
| 跨域假阳性 | ≤ 2 | 3/10（均为缺口） |

### 7.5 编造校验（真实模型）

`scripts/test_hallucination.py` 用真实模型跑边界问题：

```
Q: 我们组织配了哪些成本类型？
期望返回: 拒绝 + 边界话术
判定: 是否出现枚举清单/具体数量断言
```

实测 3/3 未编造。**新增配置类卡片后必须重跑此项。**

### 7.6 验收标准

- [ ] `validate_cards.py` 全通过
- [ ] `eval_cards.py` 本域命中率 ≥ 95%
- [ ] 新增配置卡后 `test_hallucination.py` 全通过
- [ ] 人工抽检路径与术语无误

## 8. 阶段五：关联

### 8.1 关联的三种类型

一张卡不是孤立的，它必然处在某个业务链条上：

```
        前置 ← 当前卡 → 下一步
          ↑              ↑
          └── 同类问题 ──┘
```

| 关系类型 | 例子 | 作用 |
|---|---|---|
| **上下游** | 下单 → 审批 → 跟踪 | 用户问"下单后呢"，能顺着走 |
| **父子** | 开通服务 → 配店铺ID → 配规则 | 大流程分解成小步骤 |
| **同类** | 缺成本类型 ↔ 业务类型不可用 | 一个问题解决不了，给相邻的 |

### 8.2 实测的连通结构（79 张卡，191 条边）

```
订单域（枢纽 order-task-create，被 12 张卡引用）
  order-task-create ──→ order-task-query-waybill / sdt-task-scenario-code
       ├──→ order-rule-create-limits ──→ sdt-trouble-order-method-mismatch
       ├──→ order-trouble-no-permission / order-trouble-pick-time
       └──→ order-task-config-options ──→ order-trouble-missing-cost-type

顺店通通用域（账号/权限/月结/打印/数据安全 互相串联）
  sdt-task-add-org ──→ sdt-task-add-account ──→ sdt-trouble-import-excel-error
              │                            └──→ sdt-trouble-miniapp-no-access
              └──→ sdt-rule-role-permission ──→ sdt-trouble-no-order-permission
  sdt-task-verify-monthly-account ──→ sdt-glossary-monthly-billing-modes
              │                            └──→ sdt-task-order-reconcile
              └──→ sdt-task-print-settings ──→ sdt-rule-data-security

监控/工单域
  sdt-task-monitoring-rule ──→ sdt-flow-ticket-process ──→ sdt-trouble-ticket-not-found
              └──→ sdt-glossary-monitoring-monthly-card

同城急送域
  sdt-flow-tc-service-setup ──→ sdt-rule-tc-store-config
                                      └──→ sdt-rule-tc-order-rule
                                                  │
                                         sdt-glossary-tc-cost-type
                                                  │
                                            sdt-task-tc-order
```

结构要求：每张卡**同时有入边和出边**（无孤立卡、无单向死胡同）。
79 张卡实测 0 孤立、0 断链，每张卡既有入边也有出边，全部可达。

### 8.3 关联的三个硬性要求

**要求一：不许断链**

`related` 只能指向**已存在**的卡片。
指向"计划中"的卡会造成断链，校验器会报错。

如果确实需要标记待建卡，用注释或单独的路线图文件，不放进 `related`。

**要求二：不许有孤立卡**

每张卡至少要有一个关联（出边或入边）。
孤立卡在检索时无法串联上下文，用户问追问时会断掉。

实测发现：3 张 trouble 卡最初是孤立的，补上关联后形成完整链条。

**要求三：flow 卡不重复下游细节**

这是实测踩过的坑：

```
❌ 错误：flow 卡里详细写了"怎么配店铺ID"
   → flow 卡和 rule 卡内容重叠，检索时互相抢分，
     出现"店铺ID怎么配"两张卡分数完全并列 15.56 的尴尬情况

✅ 正确：flow 卡只写"第2步：配店铺ID（详见 XX 卡）"
   → 细节留给 rule 卡，各司其职
```

### 8.4 关联如何服务答案生成

当用户问"下单后还能改吗"：

```
检索命中 order-task-create
  → 答案里提到"命中审批规则会进入待审批"
  → 顺着 related 找到 order-flow-approval
  → 用户追问"多久审批完"时，直接命中，不用重新检索
```

**这就是"业务能联通"的实际含义**：不是知识图谱的炫技，
而是让**追问时不掉链子**。

### 8.5 验收标准

- [ ] `related` 无断链（校验器自动检查）
- [ ] 无孤立卡（校验器自动检查）
- [ ] flow 卡不重复下游卡细节
- [ ] 每张卡的 `related` 至少指向 1–3 张相关卡（不是越多越好）

## 9. 检索层必须同步的规则

卡片写得再好，检索层没配套规则也会全盘失效。以下九条是实测总结，
**必须同步实现在正式检索器 `src/rag/retriever.py`**（当前只在评估脚本里）。

| # | 规则 | 不做的后果 |
|---|---|---|
| 1 | **泛化词不给分** | "怎么下单"命中所有含"下单"的卡 |
| 2 | **泛化词兜底** | 问题全是泛化词时判 0 分，反而召不回（"怎么下单"得 0.0） |
| 3 | **中文 n-gram 碎片过滤** | "怎么批量导出"产生 `么批` 这类碎片误匹配 |
| 4 | **跨字段去重计分** | 同一词在 title+one_liner+anchors 重复计分 |
| 5 | **标题命中加权** | 两张相近卡排序随机 |
| 6 | **IDF 自动降权** | 高频词（"同城急送"）淹没独特词 |
| 7 | **业务域隔离** | 问订单召回测评卡 |
| 8 | **卡型意图一致性** | 非排障问题命中报错卡 |
| 9 | **反向动作排除** | 问"导出"召回讲"导入"的卡 |

### 9.1 参数标定

```
threshold = 3.0     # 25 张卡实测：本域问题 > 10，跨域噪声 < 2（79 张卡后仍沿用 3.0，已验证）
```

**卡片数量增加后必须重新标定**——分数随卡片总数上浮。

### 9.2 意图识别的作用

```python
ACTION_INTENT = {
    "开通":   ({"开通","申请"}, {"flow"}),      # 问开通 → 优先流程卡
    "配置":   ({"配置","怎么配"}, {"rule","flow"}),
    "完成判断": ({"判断","配好","是否"}, {"rule"}),
    "区别":   ({"区别","什么意思"}, {"glossary"}),
    "限制":   ({"最多","几个","上限"}, {"rule","glossary"}),
    "下单操作": ({"下单","寄件"}, {"task"}),
}
```

意图与卡型对齐后，指标准确率提升明显（实测从 9/12 到 12/12）。

### 9.3 系统提示词的约束

```
4. 知识库没有答案时，直接说"这个问题我暂时没有资料"，不要猜
5. 如果知识库说了"以实际显示为准，我不能替你查"，
   必须原样转达，绝不能编造具体的配置值、下拉选项、数量
```

配合 `temperature=0.1`，是防编造的最后一道防线。

## 10. 新资料接入检查清单

### 10.1 接入流程（按顺序执行）

```
□ 1. 识别资料类型
     ├─ Word/钉钉文档 → import_docx.py + dws download
     ├─ Markdown 规则  → 直接读
     └─ 枚举/ErrorCode → 写扫描脚本

□ 2. 判断价值（重要）
     ├─ FAQ / 规则文档        → 高价值，优先做（实测投入产出比最高）
     ├─ 枚举 / 错误码         → 高价值，可自动生成骨架
     ├─ 操作步骤手册          → 低价值，最后做（大量依赖截图）
     └─ 前端代码              → 只做素材，不产卡

□ 3. 转换 + 清洗
     ├─ pandoc 转 markdown-pipe_tables
     ├─ 大文件用 --extract-media 分离图片
     ├─ 从目录解析标题层级（anchor ID 匹配）
     └─ 纯文本编号标题用正则还原

□ 4. 按卡型拆卡
     ├─ 判断每段属于哪类卡（task/rule/trouble/glossary/flow/state/faq）
     ├─ 一段含多种卡型 → 必须拆开
     ├─ 单卡 200–500 字，超了拆
     └─ 配置类卡片加边界话术

□ 5. 结构校验
     └─ uv run scripts/validate_cards.py --dir data/cards

□ 6. 建立关联
     ├─ 上下游：前置 → 当前 → 下一步
     ├─ 父子：大流程 → 小步骤
     ├─ 同类：相关报错互指
     └─ 确保无断链、无孤立卡

□ 7. 召回校验
     ├─ 写本域测试问题（应命中正确卡）
     ├─ 写跨域测试问题（应返回没资料）
     └─ uv run scripts/eval_cards.py --dir data/cards

□ 8. 编造校验（有配置类卡片时必做）
     └─ uv run scripts/test_hallucination.py --only-boundary

□ 9. 人工抽检
     ├─ 100% 核对菜单路径
     └─ 30% 抽查术语改写与答案完整性
```

### 10.2 常见错误速查

| 错误 | 症状 | 修法 |
|---|---|---|
| 按字数硬切 | 出现"第2部分"这种无标题碎片 | 只在标题处切 |
| 标题层级靠缩进猜 | 层级全乱 | 从目录 anchor ID 解析 |
| 正则含 `\S` | 标题首字被吃掉 | 去掉 `\S` |
| 一张卡塞多个主题 | 答非所问 | 拆卡 |
| 代码名进了 title | 业务人员看不懂 | 校验器拦截 |
| flow 卡写了细节 | 和 rule 卡抢分 | flow 只写"详见XX卡" |
| 配置卡没边界话术 | 模型编造配置值 | 加"以实际显示为准" |
| `related` 指向不存在的卡 | 断链 | 校验器拦截 |

### 10.3 质量目标

| 指标 | 目标 | 当前 |
|---|---|---|
| 结构校验通过率 | 100% | 25/25 |
| 本域召回率 | ≥ 95% | 100% |
| 跨域假阳性 | ≤ 20% | 30%（缺口导致，会随补卡下降） |
| 边界问题未编造 | 100% | 3/3 |
| 卡片平均长度 | 200–500 字 | 290 字 |

### 10.4 持续维护

卡片不是一次性工作，必须建立反馈闭环：

```
① 未命中问题 → 聚类 → 生成草稿卡 → 人工审核 → 入库
② 用户点踩   → 复审队列 → 修卡或补卡
③ 规则变更   → 按 source_ref 反查受影响卡 → 标记待验证
```

**每周**：处理未命中问题（Top 10）
**每月**：复核过期卡片，抽检低解决率卡片

详细治理机制见 `docs/knowledge-design-v2.md` §8。

## 11. 新业务接入配置

前面十章讲的是"怎么把资料变成卡片"，这一章讲**新业务接入时需要额外做什么**。

核心结论：**卡片生产方法是通用的，检索配置是业务专用的。**

### 11.1 通用 vs 需配置

| 环节 | 换业务能否直接用 | 需要做的事 |
|---|---|---|
| 摄取（docx/钉钉转换） | ✅ 完全通用 | 无 |
| 清洗（标题层级还原） | ✅ 完全通用 | 无 |
| 拆卡（卡型判定、骨架） | ✅ 完全通用 | 无 |
| 结构校验 | ✅ 完全通用 | 无 |
| 关联（related 建图） | ✅ 完全通用 | 无 |
| **业务域词表** | ❌ 必须补 | 在 `config/retrieval.yaml` 加 `domains` |
| **业务意图词表** | ⚠️ 部分复用 | 通用意图可复用，专属意图需补 |
| **阈值标定** | ❌ 需重调 | 卡片数变了分数就变 |

### 11.2 接入步骤

**第 1 步：生产卡片**

按第 4–8 章流程产出卡片，与业务是什么无关。

卡片放 `data/cards/` 下，**一个业务一个目录**：

```
data/cards/
├── order/     # 订单域
├── sdt/       # 顺店通通用
├── hr/        # 人力资源
└── finance/   # 👈 新业务只需新建一个目录
```

不按卡型再分子目录——卡型已体现在 `card_id` 里（如 `order-task-create`），
再分一层只是重复。文件名直接用 `card_id`，便于查找。

**第 2 步：声明业务域**

在 `config/retrieval.yaml` 的 `domains` 下追加：

```yaml
domains:
  # 已有业务...
  订单:
    keywords: [下单, 订单, 运单, 寄件, 收件, POD, 签收, 发货]
  # 👇 新业务只需加这一段
  财务:
    keywords: [结算, 账期, 对账, 账单, 开票, 收款, 付款]
```

**选词原则**：
- 选**该业务独有**的词（"结算""账期"），不要选通用词（"系统""管理"）
- 5–12 个词为宜，过多会让域判定过度敏感
- 涵盖：业务名词 + 核心动作 + 常见对象

**第 3 步：声明业务专属意图（可选）**

通用意图跨业务复用。只有当新业务有**专属动作**时才需要补：

```yaml
intents:
  # 通用意图（所有业务共用，无需改动）
  开通: {markers: [开通, 申请], card_types: [flow]}
  配置: {markers: [配置, 怎么配], card_types: [rule, task, flow]}
  区别: {markers: [区别, 什么意思], card_types: [glossary]}

  # 👇 财务专属（如果该业务有独特问法）
  结算操作:
    markers: [结算, 对账, 核销]
    card_types: [task, flow]
```

**第 4 步：重新标定阈值**

卡片总数变化后，分数分布会整体上浮/下降。

```bash
# 先跑一次看实际分数分布
uv run scripts/eval_cards.py --dir data/cards/财务

# 如果本域问题全部远高于阈值、跨域全部低于阈值 → 阈值合适
# 如果本域有合理问题被滤掉 → 下调 threshold
# 如果跨域噪声大量命中 → 上调 threshold
```

小语料（卡片数 < 50）时 `CardScorer` 会自动按比例下调阈值，
但仍建议人工确认一次。

**第 5 步：验证**

```bash
# 结构校验
uv run scripts/validate_cards.py --dir data/cards/财务
# 召回校验（在新业务的测试集上）
uv run scripts/eval_cards.py --dir data/cards/财务
# 有配置类卡片时，验证不编造
uv run scripts/test_hallucination.py --only-boundary
```

### 11.3 实测：新业务不配置会怎样

用「财务结算」这个未配置的业务测试：

| 问题 | 域识别 | 意图识别 |
|---|---|---|
| 结算单怎么生成 | ❌ 未识别 | ❌ 未识别 |
| 对账单在哪导出 | ❌ 未识别 | ❌ 未识别 |
| 为什么结算金额对不上 | ❌ 未识别 | ❌ 未识别 |

**后果**：域隔离失效 → 跨域误召回的概率上升；意图不匹配 → 卡型优先级失效。

所以**第 2 步（声明业务域）不是可选项**。

### 11.4 架构说明：为什么配置要外置

```
                    config/retrieval.yaml
                    （业务配置，新业务只改这里）
                            ↓
src/rag/card_scoring.py  ← 九条规则的实现（业务无关）
        ↑                ↓
        │        src/rag/retriever.py（正式检索）
        │                ↑
scripts/eval_cards.py ───┘（评估脚本，与正式检索共用同一套逻辑）
```

**关键设计**：评估脚本和正式检索器**共用同一个打分模块**。
这样评估通过就代表线上行为一致，避免"评估 100% 但线上翻车"。

### 11.5 接入检查清单

```
□ 卡片按第 4–8 章流程生产，validate_cards.py 全通过
□ config/retrieval.yaml 的 domains 已追加新业务及其关键词
□ 有专属意图的已补 intents
□ eval_cards.py 的本域测试集已包含新业务问题
□ 召回率 ≥ 95%
□ 阈值已按新卡片数确认（或让小语料自适应生效）
□ 有配置类卡片的，跑过 test_hallucination.py
□ related 无断链、无孤立卡
```

## 12. 端到端验证（实测）

第 7 章的校验只覆盖关键词打分，不涉及向量库。
真实上线前必须跑一次**完整链路**：YAML → embedding → 向量库 → 混合检索。

### 12.1 两个测试脚本的区别

| 脚本 | 覆盖范围 | 依赖 | 用途 |
|---|---|---|---|
| `eval_cards.py` | 只测关键词打分 | 无 | 快速迭代卡片内容 |
| `test_e2e.py` | 全链路（含向量库） | Ollama + ChromaDB | 上线前必做 |

**为什么要两个**：关键词测试秒级完成，适合写卡时反复跑；
端到端要调用 embedding 模型，慢但能发现向量层的真实问题。

### 12.2 实测结果（79 张卡）

| 指标 | 关键词 | 端到端 |
|---|---|---|
| 本域召回 | 100%（82/82） | **100%（82/82）** |
| 线上真实问题 | 10/10 | **10/10** |
| 编造测试 | — | 3/3 未编造 |
| 跨域假阳性 | 0/12 | — |

> 2026-11-24 全量比对资料库后：补齐 26 张卡（40→66），
> 测试集由 23 条扩到 58 条，关键词与端到端均 100%，
> 线上真实问题由 9/10 提升到 10/10（库存域已建卡）。

**向量层临界问题**：新卡首次端到端时，「数据安全怎么配」
「各个版本有什么区别」的余弦相似度落在 0.436 / 0.381，
刚低于 0.45 阈值被判空。修法不是调阈值，而是**把用户问法
写进 `one_liner` 开头**（向量化用的是 one_liner+body），
让意图词直接参与 embedding，两者随即稳定召回。

### 12.3 端到端暴露的三个真问题

这三个坑只有跑完整链路才会发现，关键词测试测不出来。

**问题一：重排候选池被提前截断**

```python
# ❌ 错误：先按 top_k 截断，再重排
items = [it for it, _ in merged[:top_k]]
items = self._rerank_with_rules(query, items, ...)
# 正确答案已被切掉，重排救不回来
```

修法：重排输入用 `max(top_k * 3, 10)` 的候选池，重排后再截断。
**效果：88% → 92%**

**问题二：IDF 基于候选池计算导致分数漂移**

同一张卡在不同大小的候选池里，IDF 不同、分数不同，排序不稳定。

修法：IDF 必须基于**全库**计算一次，结果缓存在实例上。
**效果：92% → 96%**

**问题三：向量库往返丢失字段**

`KnowledgeItem` 没有 `one_liner` 字段，写库再读回来只剩 `content`，
只能用首句还原——但首句还原会吞掉句号，导致分数失真。

修法：① 给 `KnowledgeItem` 补 `one_liner`/`module` 字段；
② **重排时优先用全库原始 YAML 卡片**，不用向量库返回的对象。
**效果：96% → 100%**

> 教训：向量库不是"无损存储"。检索重排要用原始数据，不要依赖往返后的对象。

### 12.4 端到端测试清单

```
□ validate_cards.py 全通过（结构 + 连通性）
□ eval_cards.py 本域召回 ≥ 95%
```
